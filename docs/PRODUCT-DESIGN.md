# ROMEO: стандарт удобства и фронтенд-архитектуры

Дата: 1 ноября 2026. Основание: проверка версии `6cc28d5`, браузер Chromium, экраны 1440 × 960 и 390 × 844, официальные материалы W3C и React.

Это результат исследования и аудит текущей реализации. Проблемы ниже воспроизведены; документ не означает, что они уже исправлены. Проверка не является полным аудитом соответствия WCAG или исследованием с реальными пользователями.

## Продуктовые решения

- Сохраняем белый интерфейс и Montserrat. Цвет используется для состояния и приоритета, а не для заполнения свободного места.
- Начинаем проектирование с задачи человека: увидеть финансовый результат, проверить операцию, согласовать расход, назначить или завершить задачу.
- Каждый блок отвечает на конкретный вопрос или ведёт к действию. Повторные суммы, рекламные вставки и очевидные пояснения не добавляем.
- Финансовые оговорки, влияющие на решение, остаются: прибыль до налогов, согласование без оплаты, выбранный период и магазин. Сведения об устройстве прототипа находятся в справке.
- Пользователь всегда понимает: где он находится, какие данные видит, что изменится после нажатия и что произошло после действия.
- Главный критерий — успешное выполнение задачи. Минимальное количество кликов само по себе не доказывает удобство.

## Правила компонентов

| Элемент                         | Стандарт ROMEO                                                                                                                 | Как проверять                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Основная кнопка                 | Один доминирующий приоритет в текущем контексте. Название описывает действие: «Создать задачу», «Согласовать расход»           | Результат нажатия понятен до нажатия; вторичные действия визуально спокойнее      |
| Повторяющиеся действия в списке | Одинаковое действие всегда имеет одинаковое имя, положение и оформление                                                        | Сравнить строки разных статусов и роли пользователя                               |
| Иконки                          | Значимые или редкие действия сопровождаются текстом. У иконок без текста есть доступное имя                                    | Клавиатура, экранный диктор, проверка незнакомым пользователем                    |
| Размер нажатия                  | Для основных мобильных действий целимся в 44–48 CSS px. Это проектный стандарт, а не универсальное требование WCAG AA          | Измерить область нажатия, расстояние до соседних элементов и проверить касанием   |
| Текст                           | Основной текст 14–16 px; рабочие таблицы обычно 13–14 px. Мелкие подписи не несут единственную важную информацию               | Реальный телефон, увеличение до 200%, длинные русские названия                    |
| Контраст                        | Обычный текст минимум 4,5:1; крупный текст минимум 3:1 по определению WCAG. Не округлять значение вверх для прохождения порога | Измерить вычисленные цвета текста и фактического фона                             |
| Формы                           | Постоянные подписи, понятные обязательные поля, подходящие типы ввода, ошибка возле конкретного поля                           | Пустой ввод, пробелы, неверная сумма, исправление ошибки, клавиатура              |
| Ошибки                          | Поле отмечено через `aria-invalid`; объяснение связано через `aria-describedby`. Ввод сохраняется                              | Убедиться, что понятно, что исправить, без повторного заполнения                  |
| Диалог и боковая форма          | Фокус входит внутрь, фон недоступен для взаимодействия, Tab остаётся внутри, закрытие возвращает фокус в логичное место        | Tab, Shift+Tab, Escape, глобальные сочетания клавиш, исчезновение исходной кнопки |
| Черновик                        | Закрытие, переход назад, обновление и смена контекста не должны молча уничтожать заполненные поля                              | Проверять каждый путь ухода отдельно, включая браузерную историю                  |
| Вкладки                         | Стрелки перемещают фокус; активная вкладка связана с панелью; Tab выходит из группы                                            | Проверить модель W3C APG, а не только наличие `role="tab"`                        |
| Поиск и фильтры                 | Понятна область поиска; видны активные ограничения; есть способ вернуться ко всем данным                                       | Нет результатов, смена магазина, открытие найденной записи                        |
| Таблицы                         | Сравниваемые значения выровнены, единицы указаны, действия имеют стабильное место                                              | Большие суммы, длинные названия, пустой список, узкий экран                       |
| Обратная связь                  | Результат действия виден в данных. Уведомление дополняет результат, а не служит единственным подтверждением                    | Сохранение, отмена, ошибка, повторное нажатие                                     |

WCAG 2.2 AA задаёт минимальный размер цели 24 × 24 CSS px с исключениями, включая расстояние между целями. Кнопку 32 × 32 нельзя автоматически объявлять нарушением; при этом её можно обоснованно увеличить для удобства.

## Воспроизведённые проблемы

Приоритеты: P1 — потеря работы или существенное препятствие; P2 — читаемость, последовательность и удобство. Это приоритеты продукта, не уровни WCAG.

### P1. Браузерная кнопка «Назад» теряет заполненную заявку

Шаги: Обзор → Финансы → Заявка на расход → заполнить название → «Назад» в браузере → снова открыть заявку.

Результат: форма закрывается без предупреждения; при повторном открытии название пустое. Обработчик `popstate` в `src/App.tsx` очищает `modal`, обходя проверку `protectChanges` в `src/ui.tsx`.

Решение: общий механизм черновиков и ухода со страницы. Минимально сохранять незавершённую заявку/задачу в пределах сессии и восстанавливать её; отделять черновики по роли и типу формы. Очистка — после успешной отправки или явного «Не сохранять». Одной защиты крестика и Escape недостаточно.

Критерий приёмки: введённые поля доступны после Back/Forward и обновления, либо пользователь осознанно подтвердил их удаление; данные другой роли не подставляются.

### P1. Ctrl+K выводит фокус из открытого диалога

Шаги: открыть форму заявки → Ctrl+K.

Результат: активным становится фоновое поле «Поиск по системе». Глобальный обработчик в `src/App.tsx` не учитывает открытый диалог; текущая ловушка Tab не восстанавливает фокус, уже оказавшийся снаружи.

Решение: единое управление слоями интерфейса, недоступный фон (`inert` или проверенный механизм библиотеки), ограничение глобальных сочетаний активным слоем. Проверить возврат фокуса после создания объекта, когда исходная кнопка исчезает.

Критерий приёмки: клавиатура и сочетания не активируют фон открытого диалога; после закрытия фокус остаётся видимым и логичным.

### P1. Скрытое мобильное меню остаётся в порядке Tab

Шаги: открыть страницу на ширине 390 px с закрытым меню → Tab.

Результат: фокус получает «ROMEO OS — главная» в выдвинутой за экран панели. Измеренные координаты кнопки: x = −236, правая граница = −19. У панели `inert = false`.

Решение: выключать скрытое меню из взаимодействия; кнопке открытия добавить связанные состояния `aria-expanded` и `aria-controls`. Открытое мобильное меню должно иметь предсказуемый фокус, Escape и возврат на кнопку открытия.

Критерий приёмки: фокус не попадает за экран; закрытая боковая панель не дублирует доступную мобильную навигацию для вспомогательных технологий.

### P2. Вкладки настроек не поддерживают ожидаемую клавиатуру

Шаги: фокус на «Общие настройки» → ArrowRight.

Результат: фокус остаётся на прежней вкладке. У всех трёх вкладок отсутствует `aria-controls`.

Решение: общий компонент Tabs с моделью W3C APG: связи tab/panel, один вход через Tab, перемещение стрелками и последовательная политика активации.

Критерий приёмки: ArrowLeft/ArrowRight перемещают фокус; выбранная вкладка соответствует показанной панели; Tab не перебирает всю группу вместо перехода к содержимому.

### P2. Часть вторичного текста слишком бледная

| Пример на главной                | Текст / фон           | Размер | Контраст |
| -------------------------------- | --------------------- | ------ | -------- |
| Заголовки таблицы магазинов      | `#7c7c7c` / `#f8f8f8` | 11 px  | 3,93:1   |
| Пояснение о прибыли под таблицей | `#838383` / `#ffffff` | 10 px  | 3,79:1   |

Оба образца ниже 4,5:1 для обычного текста. Значения округлены только для отображения. Это выборочная проверка, а не список всех возможных проблем контраста.

Решение: единый токен вторичного текста с проверенным контрастом; увеличить рабочие подписи без увеличения всех отступов. Белый фон сохранить.

### P2. Мобильные элементы меньше целевого удобного размера

Измерения при 390 px: меню — 28 × 40, «Создать» — 38 × 42, уведомления — 34 × 40, профиль — 32 × 32 CSS px.

Решение: увеличить область нажатия до проектного ориентира 44–48 px и пересобрать верхнюю панель так, чтобы сохранить место поиску. Можно увеличить невидимую область кнопки без увеличения самой иконки, если области соседних кнопок не пересекаются.

## Фронтенд-архитектура

Уже полезно: финансовые расчёты и ограничения ролей вынесены из JSX; маршрут и контекст представлены отдельным модулем; есть сценарные браузерные проверки. Это сохраняем.

Сейчас `App.tsx` объединяет оболочку, глобальные клавиши, формы, таблицы, уведомления и переходы между разделами. Воспроизведённый конфликт Ctrl+K и диалога показывает проблему координации этих обязанностей. Размер файла сам по себе не является причиной переписывать приложение.

Предлагаемые границы:

```text
app/                  оболочка, маршруты, активный слой, глобальные клавиши
features/overview/    обзор и очередь решений
features/finance/     отчёты, операции, заявки, черновик расхода
features/tasks/       задачи и черновик задачи
features/assistant/   вопросы, ответы, контекст
features/settings/    настройки и роли
shared/ui/            Button, Field, Tabs, Dialog, Drawer, Table, EmptyState
domain/               финансовые правила, права и переходы статусов
data/                 интерфейс доступа к данным и текущий локальный адаптер
```

- URL владеет разделом, магазином, периодом и вкладкой отчёта.
- Форма владеет черновиком, ошибками и состоянием отправки.
- Слой данных владеет записями; показатели и отфильтрованные списки вычисляются, а не дублируются в состоянии.
- Оболочка владеет активным диалогом и правилами взаимодействия с фоном.
- Визуальные компоненты не принимают финансовые решения; разрешения проверяются на границе операции, а при внедрении — также сервером.
- Цвет, размеры текста, поля ввода, фокус и отступы задаются небольшим набором токенов. Новое исключение должно иметь конкретную причину.
- Переносить по одной ответственности с сохранением поведения. Сначала Dialog/Tabs/черновики, затем экраны. Полное переписывание ради новой структуры не требуется.

## Порядок дальнейшей работы

1. Сохранность черновиков и единые правила навигации при открытой форме.
2. Диалоги, скрытое меню, глобальные клавиши и возврат фокуса.
3. Контраст, размер рабочих подписей, мобильные области нажатия.
4. Общие Tabs, Field и Button; постепенное разделение экранов.
5. Проверка с Азатом и представителями рабочих ролей, затем изменения по наблюдаемым затруднениям.

Для каждой правки фиксировать проблему, проверяемый результат и регрессионный сценарий. Новая палитра или перестановка карточек без установленной проблемы не являются отдельной целью.

## Проверка удобства с пользователями

Задания без подсказок: найти магазин с наименьшей прибылью; объяснить отличие прибыли от остатка денег; согласовать конкретную заявку; создать задачу нужному человеку; исправить ошибочный ввод без потери данных.

Смотреть на успешность, неверные переходы, возвраты, промахи и необходимость помощи. Время выполнения полезно сравнивать до/после на одинаковых заданиях, а не задавать произвольный универсальный предел. Удобство пока не подтверждено таким исследованием.

Автоматизация дополняет это: клавиатура, фон модальных окон, история браузера с черновиком, ошибки полей, контраст, 200% увеличение, узкий экран, длинные суммы, пустые результаты. Нынешние smoke/layout-тесты в основном проверяют клики, сохранение, шрифт и отсутствие горизонтального переполнения; этого недостаточно для перечисленных свойств.

## Изученные первоисточники

- [W3C APG: Modal Dialog](https://github.com/w3c/aria-practices/blob/main/content/patterns/dialog-modal/dialog-modal-pattern.html) — фокус, Tab, Escape, возврат в рабочий контекст.
- [W3C APG: Button](https://github.com/w3c/aria-practices/blob/main/content/patterns/button/button-pattern.html) — клавиатура и поведение фокуса после действия.
- [W3C APG: Tabs](https://github.com/w3c/aria-practices/blob/main/content/patterns/tabs/tabs-pattern.html) — связи вкладок с панелями и управление стрелками.
- [WCAG: Contrast Minimum](https://github.com/w3c/wcag/blob/main/understanding/20/contrast-minimum.html) — пороги контраста и определение крупного текста.
- [WCAG 2.2: Target Size Minimum](https://github.com/w3c/wcag/blob/main/understanding/22/target-size-minimum.html) — 24 CSS px, расстояния и исключения.
- [React: Thinking in React](https://github.com/reactjs/react.dev/blob/main/src/content/learn/thinking-in-react.md) — границы компонентов, минимальное состояние и его владелец.

W3C APG описывает рекомендуемые паттерны, а не заменяет полный набор требований WCAG. Размеры текста и цель 44–48 px выше — решения для ROMEO, которые нужно проверять в реальном использовании.
